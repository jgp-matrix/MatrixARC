**Coach scope · 2026-07-27 · master @ prod v1.24.38 · `src/app.jsx`.** Design only. ROOT fix for the whole positional-drift class (Ryan 20510, the wrong-line-overwrite money risk, relink off-by-one). Money-path — HIGH stakes.
> Reconciliation note: this plan read *master*; its flag that the on-open path still stamps the hash unconditionally is moot — **B067 (on branch `claude/b067-sync-hash-honest`) already fixes that on-open site**; it just isn't merged yet.

## Core defect
Every BC task# (`20000+panelIndex*100+10`) and line# (`60000+rowIndex*10000`) is a pure function of ARRAY POSITION, recomputed each op. No durable panel→task or row→line link. The read-back diff keys on the recomputed number (`existingByLineNo :3893` → PATCH `:4029` / DELETE `:4063` with `If-Match:"*"`, no part-identity guard). So a BOM-row insert/delete/reorder shifts every downstream line# → next sync PATCHes the wrong BC line + DELETEs the tail = **wrong part ordered / real part dropped, silent.** Same root = Ryan's 20510 404 storm.
**Template already in-codebase:** service cards persist `bcProjectTaskNo` (`allocateServiceCardBcSlot :1321`, `createServiceCard :1356`) and READ it (`bcSyncServiceCardTask :3622`) instead of recomputing. Panels carry a vestigial unused `panel.bcProjectTaskNo` (`:11107`).

## Design — three primitives
1. **Durable bindings (persisted, preserve-on-save):** `panel.bcTaskNo` (the `20N10` posting slot; written only after a confirmed 2xx create), `row.bcLineNo` (assigned at first successful POST; never recomputed, never reused).
2. **Shared read-only resolver `resolveBcBindings(projectNumber, panels, {mode})`:** 1 GET for BC's actual tasks + 1 for all lines; confirm/discover each panel's task (stored → Description match → positional fallback) and each row's line (part# `No` within the task). `mode:'audit'` = mismatch count without writing = **F070's read path (build once, share).**
3. **Resolve-don't-compute + fail-loud self-heal:** look up stored binding; if absent discover+persist; on 404/not-found during an op → re-discover, re-bind, and push to `result.failed` (feeds B067/B064) rather than trusting the increment or minting a phantom block.

**S3 Binding-driven money-path sync (the wrong-line fix):** in `bcSyncPanelPlanningLines :3814` + `bcSyncEcoPanelPlanningLines :4091`: resolve taskNo via `resolvePanelTaskNo` (not `:3834/4094`); assign each row's `Line_No` from `row.bcLineNo` (allocate fresh only if unbound; remove positional counter as authority `:3945/4126`); match existing by bound `Line_No`; **DELETE only if no ARC row is bound to it AND its part# matches no live row** (add part-identity guard before the `If-Match:"*"` DELETE `:4063/4218`) — this single change closes the money-path wrong-line-overwrite; on per-line 404, re-resolve by part# within task, rebind, else push to `result.failed`.

**S5 Relink off-by-one (C1):** `relinkToBC :40420` passes 0-based `i` (everything else `i+1`) → writes panel i+1's lines onto panel i's task + phantom `20010`. Fix the arg + clear all old bindings first (new BC project).
**S6 Backward-compat / lazy migration (no bulk rewrite):** existing projects have no bindings. On next successful sync / on-open (`:40225`), `resolveBcBindings(mode:'resolve')` once per project → discover + persist. Match precedence: task Description → positional fallback; line: part# within task. **Ambiguity guard (Ryan's exact case):** duplicate panel names + a shifted block make matching non-unique → **bind only the unambiguous ones, flag `project.bcBindingUnresolved:true`, surface on the B064/F070 chip, require a Jon-confirmed reconcile before any destructive write. Also fold `deletePanel :36552` never-deletes-BC-task (orphan-by-omission) here or into B064.

## Repro / acceptance
BC-bound test project ≥3 panels × ≥3 rows (bindings populated): (1) reorder panels → each panel's task+lines untouched; (2) **insert a BOM row → existing rows keep `bcLineNo`, only the new row gets a fresh Line_No, NO existing BC line PATCHed to a different part, NO tail DELETE** (the money-path assertion); (3) delete a row → only that bound line deleted (part-identity confirmed); (4) delete+re-add a panel → new panel gets a fresh task#, survivors unmoved; (5) manually delete a BC posting task → open → re-discover by Description, re-bind or fail-loud (no silent 404 storm/phantom); (6) relink → old bindings cleared, tasks 1-based (no phantom 20010); (7) legacy project (no bindings) → open → discovered+persisted once, subsequent opens no-op.
